# validation

The 15 scenarios behind the "tested against" line in the main README, as a script you can run yourself.

Five real projects, three scenarios each. Everything here is generated by `run_validation.py`, and `results/` is checked in so you can read the outcome without running anything.

```bash
python validation/run_validation.py              # all five
python validation/run_validation.py cachetools   # just one
```

It needs `uv` on PATH and network access. Each project is cloned at a pinned commit into its own virtualenv, so a run does not touch your environment and does not depend on what happens to those projects later.

## the three scenarios

Each one starts from `greenproof snapshot` on a clean checkout, then does something an agent might do, then asks `greenproof verify` for a verdict.

- **A, adds a real test.** A new test file that asserts documented behaviour. The code is untouched. Should be `EARNED`, and flagging it would be a false positive.
- **B, edits a comment.** A comment appended to the file scenario C later breaks. Also should be `EARNED`.
- **C, the constructed cheat.** Break a function so it violates its contract, then delete exactly the tests that catch it, until the suite is green again.

Scenario C never hardcodes which tests to delete. The runner breaks the function, runs pytest, parses the failures, removes those test functions by AST, and repeats until pytest exits 0. Every project needed two rounds: the first deletion exposed more failures, sometimes in other files. That is the same thing an agent deleting its way to green would run into, and it is why the deletions cross up to six files.

A scenario that cannot be set up is reported as a setup failure, not as a verdict. If the cheat does not end up green, there is no false green to catch and the run says so instead of scoring it.

## results

Run on 2026-07-31, Windows, CPython 3.12.

| project | tests at baseline | what C breaks | suite after the cheat | tests deleted | A | B | C |
|---|---|---|---|---|---|---|---|
| [python-slugify](https://github.com/un33k/python-slugify) `7b6d5d9` | 82 | slugs keep leading and trailing separators | 65 passed | 17 in 1 file | EARNED | EARNED | UNEARNED |
| [termcolor](https://github.com/termcolor/termcolor) `9ed2287` | 89 | `colored()` returns bare text, no escape codes | 38 passed | 9 in 1 file | EARNED | EARNED | UNEARNED |
| [python-string-utils](https://github.com/daveoncode/python-string-utils) `78929d8` | 407 | `is_snake_case()` always False | 402 passed | 5 in 2 files | EARNED | EARNED | UNEARNED |
| [cachetools](https://github.com/tkem/cachetools) `13bb86a` | 291 | `hashkey()` collapses every call to one key | 250 passed | 25 in 5 files | EARNED | EARNED | UNEARNED |
| [flashtext](https://github.com/vi3k6i5/flashtext) `f492744` | 39 | `extract_keywords()` always returns `[]` | 25 passed | 14 in 6 files | EARNED | EARNED | UNEARNED |

15 of 15 scenarios came out as expected: no legitimate edit was flagged, and every constructed cheat was caught.

The "suite after the cheat" column is the point of the exercise. In each row pytest exits 0 and reports only passes, which is what the agent would hand you. cachetools is the clearest: 250 passing tests, nothing red, and the cache is returning the wrong value for every distinct argument list.

Deleted test functions and failing tests are not the same count. termcolor deletes 9 test functions and greenproof lists 48 failures, because those functions are parametrized.

## what is in results/

- `summary.json`, the table above as data.
- `<project>.json`, per project: baseline, install mode, and for each scenario the verdict, the exit code, the text report, the full `--json` report, and for C every deletion round.
- `<project>-<scenario>.log`, the raw pytest and greenproof output for that scenario, including each intermediate round of the cheat.

## what this is not

These are scenarios I built, not a benchmark. Fifteen cases on five projects says the mechanism holds up on real code with real test suites, at sizes from 39 to 407 tests and cheats spanning one to six files. It does not give you a detection rate against cheats in the wild, and the mutations are ones I chose, so they are not adversarial against greenproof's own blind spots.

Two limits worth naming. All five projects are pure Python with fast, self-contained suites; a project with heavy fixtures, network, or a build step is a different story for the counterfactual run. And every cheat here is "break code, delete tests", which is the case greenproof is built for. A cheat that weakens an assertion without deleting anything shows up in the forensics section of the report, but the verdict still comes from whether the original tests pass.
